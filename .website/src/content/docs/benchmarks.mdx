## General Info

SQLStreams sustained approximately **68,000 messages/s produced and consumed**
with 1,000-byte JSON messages on an M4 MacBook Air running native PostgreSQL
18.6. 

<ThreadAside label="NOTE" title="So close">
Unfortunately we live in a cruel world and these results are only *okay* and not *nice*.
</ThreadAside>

## General Methodology

The benchmarks drive producers unpaced and measure how quickly consumers keep up.
Each scenario ran three measured repetitions from one build; the workload,
configuration, and reproduction steps are recorded separately below.

Per-message recording is disabled to avoid its JSON and disk-write overhead.
Aggregate counters measure rates and totals; they do not prove that every
individual message was handled exactly once. Detailed latency is unavailable
in these runs. The quiet scenario retains full recording for its identity
checks ([0687](/decisions/0687/)).

Keep integration tests, other database workloads, and builds out of the measured
window. The settings are tuned for this host; reproduction on another machine
measures that machine's capacity. No additional handler work is included.

See the [default settings](#default-config) shared by both scenarios.

<ThreadAside label="NOTE" title="You calling me a liar">

## Single Stream Scenario

The idea is to get the maximum **sustainable** producer / consumer throughput for a single stream.

To do that a single `orders` stream is created. An arbitrary number of producers and consumers
can be used to find the global maximum. The one caveat being only a single consumer group.

To make sure we measure the maximum **sustainable** throughput we have artifically low retention
and cleanup task polling. This in theory should only make the results worse and I'm okay with that.

### Methodology

The sustained max throughput benchmark consists of three consecutive 30-minute runs.
They each used the same frozen binary and configuration. The database was recreated
between runs however the PostgresSQL instance itself was not restarted or recreated.

Each run retains its environment, effective
settings, raw counters, backlog and storage samples, logs, and verdict.
No run was replaced or excluded.

For more detailed information:

- [Evidence directory][evidence] - Run archives and configuration.
- [Machine-readable results][summary] - Measurements and verdicts in JSON.
- [Source snapshot][source] - Exact source used for the benchmark.
- [Build manifest][manifest] - Revision, hashes, timing, and rate selection.

See the [single stream settings](#single-stream-config).

### Results

| Run | Produced/s | Consumed/s | Backlog slope, messages/s | Logged maintenance failures | Verdict |
| --- | ---: | ---: | ---: | ---: | --- |
| [1][run-1] | 74,130 | 74,129 | +5.50 | 2 | Pass |
| [2][run-2] | 68,185 | 68,188 | −0.61 | 0 | Pass |
| [3][run-3] | 66,141 | 66,152 | −2.34 | 0 | Pass |

Run 1 logged two janitor partition-drop lock timeouts and retried. Runs 2 and

### How to Reproduce

Use Go 1.27, `just`, and native PostgreSQL 18 tools. Run from the repository root
with a filled `.env` file present.

The example below uses Homebrew's PostgreSQL installation on macOS and the
[PostgreSQL configuration][postgres-config] retained with the published results.
Use PostgreSQL 18.6 to match the published server version.

Below is the reproduce script:

```sh
(
set -eu
postgres_bin="$(brew --prefix postgresql@18)/bin"
benchmark_root="$(mktemp -d /tmp/sqlstreams-benchmark.XXXXXX)"
"$postgres_bin/initdb" -D "$benchmark_root/pgdata" -U scratch \
  --auth=trust --encoding=UTF8 --locale=C
cat .bench/results/published/2026-09-11/postgresql.conf \
  >> "$benchmark_root/pgdata/postgresql.conf"
"$postgres_bin/pg_ctl" -D "$benchmark_root/pgdata" \
  -l "$benchmark_root/postgres.log" start
trap '"$postgres_bin/pg_ctl" -D "$benchmark_root/pgdata" stop -m fast' EXIT

export POSTGRES_HOST=127.0.0.1 POSTGRES_PORT=55439
export POSTGRES_USER=scratch POSTGRES_PASSWORD=''
export GOMAXPROCS=4 GOGC=400 GOMEMLIMIT=2GiB
for benchmark_run in 1 2 3; do
  export POSTGRES_DB="benchmark_$benchmark_run"
  "$postgres_bin/createdb" -h "$POSTGRES_HOST" -p "$POSTGRES_PORT" \
    -U "$POSTGRES_USER" "$POSTGRES_DB"
  just bench max-throughput 1 5m 1 1 on native
  "$postgres_bin/dropdb" -h "$POSTGRES_HOST" -p "$POSTGRES_PORT" \
    -U "$POSTGRES_USER" "$POSTGRES_DB"
done
just bench-report max-throughput
)
```

This creates a dedicated native cluster, runs the current `max-throughput`
scenario three times with a fresh database each time, and stops the cluster
afterward. Native execution accepts one repetition per invocation, so the loop
owns database creation and cleanup. The server stays running between runs.

The arguments for `just bench max-throughput` are:

| Argument | Name | Value |
| --- | --- | --- |
| `$1` | Time scale | `1` |
| `$2` | Drain budget | `5m` |
| `$3` | Repetitions | `1` |
| `$4` | Consumer process replicas | `1` |
| `$5` | Synchronous commit | `on` |
| `$6` | Execution mode | `native` |

## Multi Stream Scenario

The idea is to see how producer / consumer throughput changes as we add more streams.

To do that we run the same workload over 1, 4, and 16 streams. Each stream has
an independent `fraud-scoring` and `analytics` consumer group, so every message
is handled twice.

These are short **burst** measurements. Unlike the single-stream scenario,
messages do not expire and scheduled vacuum is suspended.

### Methodology

Each stream count ran three consecutive repetitions with a 30-second warmup
and a two-minute measured hold. They each used the same frozen binary and
configuration. Docker Compose recreated the database cluster between runs.

For more detailed information:

- [Run ledgers][multistream-evidence] - Measurements and verdicts.
- [Scenario source][multistream-scenario] - Workload and settings at the recorded revision.
- [Compose configuration][multistream-compose] - Postgres settings and container limits.

See the [multi stream settings](#multi-stream-config).

### Results

| Streams | Produced/s | Consumed/s, all groups | Backlog slope, messages/s | PostgreSQL CPU, cores | WAL per message |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 43,027 | 37,861 | +23,482 | 3.7 | 2.2 KB |
| 4 | 42,641 | 77,892 | +2,015 | 6.1 | 2.0 KB |
| 16 | 45,558 | 83,185 | +300 | 5.7 | 2.1 KB |

Produced rates count messages written. Consumed rates count messages handled across
both groups. Each message is handled twice, so keeping up requires a consumed rate
roughly twice the produced rate.

The runs were back to back, and each repetition produced up to ten percent
less than the one before it. These two-minute
holds do not establish sustainable throughput.

### How to Reproduce

Use Go 1.27, `just`, and Docker with Compose running. Run from the repository
root with a filled `.env` file present.

Below is the reproduce script:

```sh
(
set -eu
for benchmark_streams in 1 4 16; do
  just bench "multistream-unpaced-$benchmark_streams" 1 5m 3 1 on compose
  just bench-report "multistream-unpaced-$benchmark_streams"
done
)
```

This runs each stream count three times with a fresh Compose stack for each
repetition, then prints the medians.

The arguments for `just bench multistream-unpaced-4` are:

| Argument | Name | Value |
| --- | --- | --- |
| `$1` | Time scale | `1` |
| `$2` | Drain budget | `5m` |
| `$3` | Repetitions | `3` |
| `$4` | Consumer process replicas | `1` |
| `$5` | Synchronous commit | `on` |
| `$6` | Execution mode | `compose` |

Each consumer process runs the scenario's two instances per group. The commands
use the current checkout; the published runs used revision `52cfcb2c`.
