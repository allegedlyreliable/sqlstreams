SQLStreams **is** designed to be a poor man's Kafka. It is for smaller projects
that want the rich features that a message log provides but don't want
the hassle of setting up and maintaining an unfamiliar message broker.

SQLStreams **is not** designed for many enterprise use cases. While latency
and throughput should, in theory, be sufficient for most use cases at low
to medium scale, if you have extreme reliability, distribution, throughput,
or governance constraints, look elsewhere.

Always weigh your options for current and future success. And give these
other messaging platforms some love, as they heavily inspired much of what
SQLStreams is:

- [Kafka](https://github.com/apache/kafka)
- [NATS](https://github.com/nats-io)
- [River](https://github.com/riverqueue/river)

So, with that out of the way, let's really answer the question "Why SQLStreams?"

## Background

<ThreadAside label="NOTE" title="Gotta go fast">
If you are already familiar the differences between a **log** and a **queue** you can skip this part.
</ThreadAside>

Let's first set some understanding. Queues and logs are different and they each excel at different
things.

Queues are conceptually the easier thing to understand. They are your *distributed arrays*.
You push things to them and pop things off of them. That simplicity allows for some pretty amazing
features like delay, retry backoff, priority, and many more.

Logs, on the other hand, are append-only, *immutable*, distributed arrays. You push your data to
the log, and even if something reads that data, it stays there. This naturally leads to consequences
like a cursor to keep track of where the reader of the log is. These two seemingly simple differences
from a queue lead to some interesting outcomes like replay, independent consumers, and history.

## It's a message Log

<ThreadAside label="NOTE" title="Gotta go fast">
If you are already familiar with Kafka you can skip this part.
</ThreadAside>

SQLStreams, at its core, is a message **log**. As such, you get all of the beautiful features a log provides.

When you start off using a message **log**, the emails, activity feed, and promotional campaigns all derive from a single
stream, each with its own consumer group. As long as you've retained that history, you can use it to add new features
or rebuild existing ones as requirements change.

## It's a message Log... AND a retry queue

By design, queues and logs solve similar but distinct problem sets, and SQLStreams tries to utilize both
where they each naturally shine.

A **Stream** in SQLStreams is both a message log AND a retry queue. When you *produce* a message onto
a stream, it is stored in an append-only `message_log` table. From here, you can have many independent
consumer groups read and act on that data in real time. However, if an error occurs in your consumer,
the message, by default, will be stored in an `exception_queue` and retried till it either succeeds or is
marked *dead*.

The automatic combination of these two gives, in my opinion, the most natural user experience for how
a messaging platform should function. *Natural* is the key word here, though. There are consequences of this
design like no automatic circuit breaker and, by default, out-of-order retry processing.

SQLStreams **is** opinionated and aims to give you a message log without having to build the retry queue yourself.
